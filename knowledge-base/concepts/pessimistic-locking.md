# Пессимистичная блокировка (SELECT … FOR UPDATE)

Способ не допустить гонок при изменении баланса/позиции во время сделки. Перед
изменением строка пользователя блокируется в БД, пока транзакция не завершится —
параллельные сделки того же пользователя выполняются строго по очереди.

## Как в проекте (`4-db-service`)
Внутри одной `@Transactional`:
```sql
SELECT * FROM users WHERE id = ? FOR UPDATE;            -- блокируем строку юзера
SELECT * FROM portfolio_positions
   WHERE user_id = ? AND instrument_id = ? FOR UPDATE;  -- и строку позиции
```
Далее: проверка баланса/наличия бумаг → расчёт по текущей цене (из Redis `quote:last`)
→ обновление позиции и баланса → запись `Order`. Цена берётся сервером, не клиентом.

## Почему так
- Деньги — критичные данные: оптимистичная блокировка дала бы частые конфликты на
  «горячем» пользователе. Пессимистичная гарантирует корректность.
- Это сильная часть эталона, которую мы сохраняем (см. `[[adr-0001-backend-stack]]`).

## Цена за корректность
Блокировки сериализуют сделки одного пользователя и нагружают пул соединений. При 10k
клиентов критичен размер пула Hikari и `max_connections` Postgres — учитываем в
нагрузочном тесте.
